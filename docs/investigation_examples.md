# Investigation Examples

## 1. Purpose

This document provides illustrative investigation scenarios for alerts generated by the Windows Event Log Analyzer.

The scenarios are educational examples. They do not represent real incidents or actual collected telemetry.

## 2. Scenario A — Repeated Failed Logon Attempts

### Situation

The analyzer processes five Windows Security Event ID 4625 records from the same source IP within five minutes.

Example:

| Attribute | Value |
|---|---|
| Source IP | `192.0.2.10` |
| Event ID | `4625` |
| Failed attempts | 5 |
| First observed | 10:00:00 UTC |
| Last observed | 10:04:00 UTC |
| Rule | `WIN-AUTH-001` |
| Severity | High |

### Detection Result

The configured threshold is reached inside the configured time window.

An alert is generated.

### Investigation Steps

1. Identify the source IP.
2. Determine whether the address belongs to an internal host, VPN, proxy, or external source.
3. Review the targeted usernames.
4. Examine related authentication events.
5. Search for successful logons involving the same accounts.
6. Determine whether the activity matches expected user or application behavior.
7. Document the investigation.

### Analyst Considerations

Repeated failed logons may indicate brute-force activity, but they may also result from a misconfigured service or a user repeatedly entering an incorrect password.

Additional evidence is required before classifying the activity as malicious.

## 3. Scenario B — Failed Logons Below the Threshold

### Situation

The analyzer processes four Event ID 4625 records from the same source IP within five minutes.

Default threshold: five attempts.

### Expected Result

No `WIN-AUTH-001` alert is generated because the threshold has not been reached.

### Analyst Considerations

The absence of an alert does not establish that the activity is harmless.

An attacker may operate below the configured threshold or distribute attempts across multiple IP addresses.

Detection thresholds should be evaluated against the environment's normal authentication behavior.

## 4. Scenario C — Repeated Failures Outside the Time Window

### Situation

Five failed logon events originate from the same IP address, but they are spread across a period longer than five minutes.

### Expected Result

The default rule does not generate an alert unless at least five events fit inside the same five-minute sliding window.

### Analyst Considerations

The rule is designed to identify concentrated activity rather than simply count all historical failures.

Longer-term patterns may require additional detection rules.

## 5. Scenario D — Invalid or Missing Source IP

### Situation

An Event ID 4625 record has a missing or invalid source IP address.

### Expected Result

The detector ignores that event because it cannot group the event by a valid source IP.

### Analyst Considerations

This behavior can reduce detection coverage.

The analyst should inspect the original event and consider whether the authentication source can be identified using other event fields or telemetry.

## 6. Investigation Checklist

For a generated authentication alert:

- [ ] Validate the source IP.
- [ ] Identify the affected accounts.
- [ ] Review related Event ID 4625 records.
- [ ] Search for successful authentication events.
- [ ] Check whether the source is a known system or service.
- [ ] Correlate with other security telemetry.
- [ ] Determine whether the activity is expected or suspicious.
- [ ] Document the conclusion and supporting evidence.

## 7. Important Notes

An alert is an investigation starting point, not a final incident verdict.

The current implementation does not automatically block source IP addresses, disable accounts, or perform incident response actions.

Analyst validation and environmental context are required before taking defensive action.
